1. Implementation objective and deviation log

1.1 What was implemented

A bounded, isolated Docker laboratory in which a scenario controller drives harmless HTTP traffic through two internal network segments, records an independent ground-truth journal (onset_ts, escalation_ts, milestone_ts), and is observed by two distinct sensors: an application gateway event log and a restricted tcpdump sidecar whose PCAP is re-read offline by Zeek. On top of that, three collection policies (fixed, uniform random, strategic EXP3-style) produce three different training corpora, which are evaluated against one frozen held-out test set to answer the research question:

Under a matched collection budget and a common frozen test set, does a bounded strategic scenario selector produce a detector that warns earlier, or with fewer false alarms, than fixed or uniform-random selection?

2.4 The checksum caveat, and how it was handled honestly

The container veth leaves NIC transmit offloading in place, so the captured TCP checksums are invalid. Measured on the raw trace:

  • strict Zeek (checksum validation enabled) → 15,376 connection records with orig_pkts=0, orig_bytes=0, history="C" (control packets only) and bad_TCP_checksum weird events — Zeek discards the payload of every data segment and splits them differently;
  • Zeek -C (checksum validation bypassed) → 7,688 connections, all with positive bytes, service=http, port 8080.

setup/pcap_checksum_repair.py therefore derives a copy in which only the IPv4/TCP/UDP checksum fields are recomputed from the captured payload. The tool proves its own minimality: it compares the two buffers and asserts that no byte outside the checksum fields changed. The repaired trace was then re-read by Zeek with checksum validation enabled, yielding 7,688 connections with positive bytes and zero weird.log entries — and exactly the same connection count as the independent -C read of the raw trace. (The earlier 24-episode pilot showed the same pattern at its own scale: 1,936 discarded records under strict validation versus 968 usable connections.)

  • The raw PCAP is never modified; its SHA256 is recorded in the audit.
  • The audit sets checksum_validation_ignored: false and checksum_repaired: true, and carries an explicit caveat string.
  • The repair is applied only because the -C count and the repaired-strict count agree; a mismatch would downgrade the run to ZEEK_CONDITIONAL.

This is a documented, reproducible remediation of a known capture artefact, not a way of manufacturing bytes. Byte counters in every reported metric come from Zeek's own reassembly of captured payload.

3. Scenarios, independent ground truth and the early-warning definition

3.1 Scenario space

  • Development families (3): rapid_repeat (fast repeated requests to one service), destination_shift (destination alternates), jittered_burst (alternating fast/slow pauses).
  • Held-out family (1): slow_ramp — a gradual decrease of the inter-request pause. Never used for training or threshold selection.
  • Benign variants (4): steady, maintenance_burst, service_fanout, approved_bulk (includes 2 KiB transfers). These are deliberately not all "easy" negatives: maintenance_burst is behaviourally close to rapid_repeat, which is why a rate-based rule cannot separate them.

3.2 Independent ground truth

onset_ts (request 5), escalation_ts (12) and milestone_ts (19) are written by the controller before any model runs and are never derived from a detector output. The milestone is a harmless 2 KiB dummy transfer to the other service. The controller validates start < onset < escalation < milestone < end before publishing a round.

3.3 Early-warning definition (unchanged from Phase 2)

valid early warning at t_alert  iff  t_onset <= t_alert < t_milestone
lead time L_e                     =  t_milestone - t_alert      (valid warnings only)

A pre-onset alert is not a valid early warning; a post-milestone alert is a late detection; an incident with no alert is a miss. Coverage-adjusted mean lead assigns zero to every unwarned incident. Two coverage measures are reported:

  • pre_milestone_coverage — an alert exists in [onset, milestone);
  • strict_first_alert_coverage — the episode's first alert of any kind already lies in [onset, milestone). This is the honest measure of pre-impact warning, because a detector that fires before onset has not demonstrated any reaction to the anomalous stage.

5. Baselines, budgets, tuning and the CPU environment

  • Rule/rate baseline — a transparent rule on one causal feature (rate_per_s), referenced to the benign training distribution (5th/95th percentile). No learning, fully auditable.
  • Isolation Forest — trained on benign training windows only (the documented training assumption), contamination="auto", StandardScaler fitted inside the pipeline on those windows only.
  • Random Forest — supervised, class_weight="balanced_subsample", 150 trees, fixed seed 20261115, n_jobs capped at 2.
  • Compact GRU (optional) — 1-layer GRU, hidden 32, 12 epochs, device=cpu, 2 torch threads, checkpoint written after every epoch. It is a temporal model and not a graph model. Total runtime 10.5 s for all three policies.
  • Alert rule — one threshold per (policy, model), chosen on validation episodes only, subject to a declared false-alarm budget of false-positive episode rate ≤ 0.15 and pre-onset warning rate ≤ 0.15 on validation. The candidate grid spans 0.05–0.999 because a saturating model otherwise cannot exclude a false alarm at all. If no candidate satisfies the budget the run is recorded as threshold_unavailable_under_constraint — an admissible failure, never a relaxed budget.
  • Environment — Ubuntu 26.04, kernel 7.0.0-42, Intel i5-6500 (4 cores), 14.95 GiB RAM, no CUDA (torch 2.7.1+cpu, cuda_available False), Docker 29.9.3, Compose v5.7.1, Zeek 9.0.1, Python 3.12.7 in .venv; OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS=2. 6.2 The honest reading of the policy comparison

The headline coverage numbers are not sufficient to rank the policies, and the strict first-alert measure changes the interpretation completely:

  1. Fixed + Random Forest is the only configuration in seed 1 that combines high warning coverage (0.958) with a strict coverage of 0.917 — i.e. its first alert really does arrive after onset and before the milestone. Its price is a very high false-alarm rate: 0.625 of benign episodes alarm (1,612 false alarms per benign hour). That is not a usable detector; it is a sensitive detector.
  2. Strategic + Random Forest reaches coverage 1.000 with by far the lowest false-alarm rate (0.083, 215 FA/h) — but 23 of 24 incident episodes also carry a pre-onset alarm, so its strict coverage is 0.042. Its "valid early warnings" are, in almost every episode, alarms that began before the anomalous stage started. Under the strict definition, this configuration does not demonstrate pre-impact warning. The candidate mechanism is visible in the controller journal: the EXP3 selector chose destination_shift in 11 of 24 strategic rounds (fixed 8/8/8, random 5/11/8), so the strategic training corpus is skewed towards a destination-diversity signature that is also present in the pre-onset warm-up of the held-out episodes. Section 6.6 shows that this pre-onset artefact does not reproduce in the independent second seed, so it must be read as a seed-specific instability and not as a structural property of the strategic policy.
  3. Isolation Forest never warns. With the declared budget the best admissible threshold is 0.999 and the model produces zero alerts, zero coverage and zero false alarms. Its PR-AUC (0.79–0.83) is non-trivial, so the anomaly ranking exists, but no operating point survives the false-alarm constraint. This is a genuine negative result, not a bug.
  4. The rule/rate baseline is capped at 0.333 coverage because the benign maintenance_burst variant is behaviourally indistinguishable from rapid_repeat at the request-rate level.

A note on the rule ablation: with the temporal features removed, the rule baseline is re-pointed to bytes_mean (the surviving non-temporal reference), because a rule that still read rate_per_s would not have been an ablation at all. src/code/models.py now raises if a rule references a feature outside its declared set, so this cannot silently recur.

Error analysis highlights

  • False alarms dominate the fixed and random policies: 15/24 and 24/24 benign episodes alarm. The benign maintenance_burst variant is the principal confuser.
  • The Isolation Forest produces zero alerts at every admissible threshold; its ranking ability (PR-AUC ≈ 0.8) is not convertible into an operating point that respects the false-alarm budget.
  • Pre-onset alarms occur in 23/24 incident episodes for strategic/RF and 1/24 for fixed/RF; every other configuration has none. This single column is the most consequential in the whole study.
  • Misses: 16/24 incident episodes are missed by the rule baseline and 24/24 by the Isolation Forest; the Random Forest misses 0 (strategic), 1 (fixed) and 4 (random) episodes.
  • Uncertainty: episode-level bootstrap CIs (500 resamples, seed 20261115) are attached to every coverage and false-alarm figure in results.json. With 24 incident episodes per configuration the intervals are wide; the strategic-vs-random difference in false-alarm rate (0.083 vs 1.000) is large relative to its interval, whereas the coverage differences between fixed and random are not.

8. Literature comparison (method-level, not numeric)

outputs/reports/<run>/literature_comparison.csv — 15 unique references extracted from the PDFs held in researchPapers/base-papers/.

The held references work almost exclusively on public benchmark datasets (NSL-KDD, UNSW-NB15, CIC-IDS2017/2018, CTU-13, ToN-IoT, Edge-IIoTset, BoT-IoT, CICIoT2023) with offline feature vectors, and they are dominated by graph neural network and transformer architectures, several with adversarial-training or reinforcement-learning components.

Their reported scores are not comparable with the numbers in this report, for four independent reasons:

  1. Different data. These benchmarks contain real attack captures with labelled attack tools; this laboratory contains controlled, harmless HTTP behaviour profiles generated by a scenario controller.
  2. Different observation source. Their features come from offline dataset rows; here the network features are computed from a live captured TCP trace re-read by Zeek, and the ground truth comes from a controller journal.
  3. Different split and label semantics. Their splits are table-level random or time-based splits of a fixed corpus; here the split is by whole episode, decided before windowing, with a frozen test set that includes a held-out behaviour family.
  4. Different task. Several papers predict the next victim or perform multi-stage attack attribution; this study measures detection and pre-milestone warning with a strict definition, and does not attempt future-stage prediction.

The legitimate comparison is therefore mechanistic: the literature shows that graph and attention architectures dominate current intrusion-detection research; this study deliberately implements the simplest defensible baselines so that the contribution of the collection policy can be isolated from the contribution of the model. The most transferable insight from the literature for this project is the reported cross-dataset distributional drift problem, which is the same phenomenon measured here as the seen-family → unseen-family collapse of the rule baseline.

9. Limitations and threats to validity

  1. Synthetic, harmless profiles. Every "incident" is a controlled timing or destination pattern. Nothing here demonstrates detection of real malware, exploitation or exfiltration. No zero-day claim is made or supported.
  2. Two seeds only. The main results come from seed 20261115; one independent replication (seed 20261116) was collected and evaluated under the identical protocol (§6.6). It shows that the capture and sensor pipeline replicates exactly, but that the coverage ranking of the collection policies does not - it changes with the seed. The study remains exploratory; two seeds cannot establish a ranking, and further seeds would be required for a claim of that kind.
  3. One topology. A single two-segment Docker configuration exists, so topology generalisation is untestable and is listed as unavailable.
  4. Checksum caveat. The raw capture carries invalid TCP checksums from NIC transmit offloading. The reported Zeek results come from a derived copy with recomputed checksum fields, re-read with checksum validation enabled and corroborated by an independent -C read with an identical connection count. The raw PCAP is preserved unmodified. On a host where offloading can be disabled without changing system configuration, the gate would produce SENSOR_VALIDATED on the raw trace directly.
  5. Small statistical power. 24 incident and 24 benign test episodes; 8 validation episodes per class per policy. The false-alarm budget of 0.15 is only just estimable, and bootstrap intervals are wide.
  6. Heuristic strategic reward. The EXP3 selector's reward is a heuristic function of inter-request timing and destination diversity computed by the controller (game_reward()), not measured detector feedback. This is a bounded scenario-selection bandit, not a validated co-evolution or Nash-equilibrium defence.
  7. Behavioural separability. The development families are highly separable in this lab (PR-AUC up to 1.000 for the RF). Such scores reflect a simple synthetic laboratory and must not be read as production NIDS performance.
  8. No graph model. The graph component of the proposal is not implemented; unique_links and unique_destinations are aggregate features, not a graph neural network.
  9. No future-stage prediction. Prediction of a future milestone was not attempted because no independently defined future-positive set was built.
  10. Response/containment recommendations were out of scope for Phase 3.

10.3 Raw evidence is distributed separately from Git

The raw evidence — the PCAPs, the per-request gateway log, the controller journal and the Zeek connection logs — is intentionally outside Git: .gitignore excludes *.pcap, src/data/raw/* and derived bulk logs so that packet records and multi-megabyte datasets are never committed. The repository alone reproduces the analysis from the derived study tables, but not the raw capture. The raw run directories and the figures' source data are supplied in the submission evidence bundle (submission_manifest.json, SHA256SUMS.txt, README_REPRODUCE.md and the archive whose hash is recorded there), built by setup/package_phase3_submission.py. If the archive is absent, the exact missing paths are listed by that tool and no claim of end-to-end reproducibility is made.
